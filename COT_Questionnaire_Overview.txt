================================================================================
  1. OVERVIEW OF THE QUESTIONNAIRE STRUCTURE
================================================================================

The COT questionnaire is organized into 5 thematic sections containing a
total of 10 main questions (some with conditional follow-up sub-questions).
It targets 7 measurable "categories" for the purposes of progress tracking.

The questionnaire is the primary input mechanism for Phase 1 of COT. Its
purpose is to capture enough information about a new or modified use case so
that the system can:

  (a) Identify which MAGICIAN modules are affected by the change;
  (b) Identify which specific characteristics within those modules need
      reconsideration;
  (c) Indicate what type of adaptation is required (retraining, process
      change, problem reformulation, etc.);
  (d) Raise explicit flags where human validation, additional data, or
      further preparation is required before deployment.

The 5 sections and their corresponding category weights are:

  Section A – Robot Configuration     →  Category 1: Robot Arms
  Section B – Sensors & Perception    →  Category 2: Camera / Sensors
                                          Category 3: Lighting
  Section C – Material & Properties   →  Category 4: Material / Object Size
                                          Category 7: Mesh Availability
  Section D – Defect Detection        →  Category 5: Defect Types
  Section E – Time & Priority         →  Category 6: Time / Profit


================================================================================
  2. PROGRESS & CONFIDENCE SCORING
================================================================================

The questionnaire tracks 7 categories. Each category contributes 1 point to
the overall confidence score. A category is considered "answered" according to
the following rules:

  Category 1  (Robot Arms)      : The "Number of robot arms" dropdown has a
                                   non-empty selection.

  Category 2  (Camera/Sensors)  : Either the "Camera type" dropdown has a
                                   non-empty selection, OR at least one
                                   checkbox in "Additional sensor modalities"
                                   is checked.

  Category 3  (Lighting)        : The "Lighting conditions" dropdown has a
                                   non-empty selection.

  Category 4  (Material/Size)   : At least one material checkbox is checked,
                                   OR the "Object sizes" dropdown has a
                                   non-empty selection.

  Category 5  (Defect Types)    : At least one defect type checkbox is checked.

  Category 6  (Time/Profit)     : Either the "Time constraints" dropdown has a
                                   non-empty selection, OR the
                                   "Profit/priority definition" dropdown has a
                                   non-empty selection.

  Category 7  (Mesh)            : The "3D mesh availability" dropdown has a
                                   non-empty selection.

Confidence levels:
  0 – 39%  → LOW    → "Answer more questions for better recommendations"
  40 – 69% → MEDIUM → "Good start, consider filling remaining fields"
  70 – 100%→ HIGH   → "Comprehensive configuration provided"

  3. SECTION A — ROBOT CONFIGURATION
================================================================================

------------------------------------------------------------------------
  Q1. Number of robot arms
------------------------------------------------------------------------

PURPOSE:
  Determines the physical robot topology. This has direct implications for
  how the Grabber module manages its sensor peripherals and how the
  Orienteering Solver formulates the scheduling problem.

TOOLTIP SHOWN TO USER:
  "Select whether your setup uses a single robot arm or multiple coordinated
   arms. Multiple arms are needed for tasks requiring parallel operations or
   accessing multiple sides of large objects."

AVAILABLE ANSWERS:
  ┌──────────────────────────┬────────────────────────────────────────────────┐
  │ Option                   │ Meaning                                        │
  ├──────────────────────────┼────────────────────────────────────────────────┤
  │ Single robot arm         │ Standard single-arm configuration; default OP  │
  │                          │ formulation is the Orienteering Problem.        │
  ├──────────────────────────┼────────────────────────────────────────────────┤
  │ Multiple robot arms      │ Two or more arms operating in coordination.     │
  │                          │ Triggers follow-up sub-question.               │
  └──────────────────────────┴────────────────────────────────────────────────┘

CONDITIONAL FOLLOW-UP (shown only when "Multiple robot arms" is selected):
  Sub-question : "How many robot arms?"
  Input type   : Numeric integer field (min=2, max=10, default=2)
  Purpose      : Quantifies the number of arms to scope multi-arm
                 process configuration and problem formulation.

─────────────────────────────────────────────────────────────────
  CONSEQUENCES OF Q1
─────────────────────────────────────────────────────────────────

  Answer: "Single robot arm"
  ─────────────────────────
  No characteristics are triggered. The system operates in its default
  single-arm configuration. No module adaptations are flagged.

  Answer: "Multiple robot arms"
  ──────────────────────────────

  [MODULE IMPACT 1] Grabber
    Characteristic  : "Multiple robot arms"
    Affects         : Process
    What changes    : The Grabber must execute multi-threaded peripheral
                      management to handle parallel sensor data streams from
                      multiple robot arms simultaneously. The existing
                      threading architecture (Arduino_Thread, ATI_Thread,
                      Teensy_Thread, GiGE_Thread) must be extended to
                      support concurrent operations for each arm.
    Scope of change : Process-level change; no input interface change
                      required but software concurrency architecture must
                      be verified.

  [MODULE IMPACT 2] Orienteering Solver
    Characteristic  : "Multiple robot arms"
    Affects         : Problem Description
    What changes    : The scheduling problem formulation changes from the
                      standard Orienteering Problem (OP) to the Team
                      Orienteering Problem (TOP). In TOP, multiple agents
                      (robot arms) must cooperatively share and schedule
                      defect remediation tasks. The Algorithm process and
                      the Hyperparameters process must be reviewed and
                      reconfigured to support multi-agent scheduling. The
                      Problem_description process is fundamentally altered.
    Scope of change : The entire problem definition changes. The DefectProfit-
                      Calculator and Threshold processes remain applicable
                      but must account for multi-agent scenarios.

  [FLAG RAISED] Human Validation Required: Multi-Arm Coordination
    Type    : Human oversight flag
    Message : "Team Orienteering Problem formulation and arm synchronisation
               must be reviewed by a robotics engineer."
    Reason  : The transition to a multi-agent scheduling problem introduces
              non-trivial coordination requirements that cannot be verified
              automatically. A domain expert must validate the formulation
              before deployment.

  Q2. Camera type
------------------------------------------------------------------------

PURPOSE:
  Identifies the type of vision sensor used in the setup. This affects
  whether the Grabber module requires special configuration beyond its
  default ARAVIS-based GiGE camera integration.

TOOLTIP SHOWN TO USER:
  "Choose the type of camera system you're using. GiGE cameras require
   specific configuration for industrial applications. Select 'Other' if
   using specialized cameras like thermal or hyperspectral."

AVAILABLE ANSWERS:
  ┌────────────────────────────────┬──────────────────────────────────────────┐
  │ Option                         │ Meaning                                  │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ Standard/Default camera        │ The system's built-in default camera     │
  │                                │ configuration is used. No extra config   │
  │                                │ required.                                │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ GiGE camera                    │ A GigE Vision industrial camera is used. │
  │                                │ Triggers follow-up field.                │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ Other camera type              │ A non-standard camera (e.g., thermal,    │
  │                                │ hyperspectral, depth-only). Triggers     │
  │                                │ follow-up field.                         │
  └────────────────────────────────┴──────────────────────────────────────────┘

CONDITIONAL FOLLOW-UP (shown when "GiGE camera" or "Other camera type"):
  Sub-question : "Specify camera model/type:"
  Input type   : Free-text field
  Placeholder  : "e.g., Basler acA1920-40gc, FLIR thermal camera..."
  Purpose      : Records the specific camera model for documentation and
                 to inform partners of hardware-specific considerations.

─────────────────────────────────────────────────────────────────
  CONSEQUENCES OF Q2
─────────────────────────────────────────────────────────────────

  Answer: "Standard/Default camera"
  ──────────────────────────────────
  No specific characteristic triggered. The Grabber module's GiGE_Thread
  (using ARAVIS SDK) operates in its standard configuration.

  Answer: "GiGE camera" OR "Other camera type"
  ─────────────────────────────────────────────

  [MODULE IMPACT] Grabber
    Characteristic  : "Usage of a different GiGE camera"
    Affects         : Input
    What changes    : Because the Grabber module is built on the ARAVIS SDK,
                      which is a generic library compatible with all GigE
                      Vision-compliant cameras, NO software change is required
                      when swapping between GiGE camera models. The GiGE_Thread
                      process handles the low-level protocol abstraction
                      automatically.
    Important note  : Even though "no change is needed", this characteristic
                      is flagged so that partners are explicitly aware that
                      camera selection has been reviewed and confirmed
                      compatible. For "Other camera type" (e.g., thermal or
                      hyperspectral), additional investigation may be needed
                      outside the scope of this characteristic.
    Scope of change : Input-level acknowledgement; no process changes needed
                      for standard GiGE camera swaps.

  Q3. Additional sensor modalities needed
------------------------------------------------------------------------

PURPOSE:
  Identifies whether the use case requires sensing modalities beyond the
  standard camera setup. The Grabber is designed to be extended with
  additional sensors via its multi-threaded architecture.

TOOLTIP SHOWN TO USER:
  "Select additional sensors needed beyond vision. Tactile/force sensing
   helps detect surface properties through touch. Additional vision sensors
   can provide different angles or specialized imaging."

AVAILABLE ANSWERS (checkbox — multiple can be selected simultaneously):
  ┌──────────────────────────────┬────────────────────────────────────────────┐
  │ Option                       │ Meaning                                    │
  ├──────────────────────────────┼────────────────────────────────────────────┤
  │ Tactile/Force sensing        │ The use case requires physical contact      │
  │                              │ sensing using force/torque sensors and/or  │
  │                              │ accelerometers (e.g., for surface texture  │
  │                              │ or defect detection by touch).             │
  ├──────────────────────────────┼────────────────────────────────────────────┤
  │ Additional vision sensors    │ The use case requires more than one camera  │
  │                              │ or a secondary vision system (e.g.,        │
  │                              │ multi-angle, stereo vision, secondary      │
  │                              │ depth sensor).                             │
  └──────────────────────────────┴────────────────────────────────────────────┘

  Note: Neither, one, or both options can be selected. If none are selected,
        no additional sensor characteristic is triggered.

─────────────────────────────────────────────────────────────────
  CONSEQUENCES OF Q3
─────────────────────────────────────────────────────────────────

  Answer: Any checkbox selected ("Tactile/Force sensing" and/or
          "Additional vision sensors")
  ─────────────────────────────────────────────────────────────────

  [MODULE IMPACT] Grabber
    Characteristic  : "Addition of an extra sensor modality"
    Affects         : Process
    What changes    : The Grabber's processing architecture must be extended
                      to handle the new data stream. Two approaches exist:

                      Option A — Use existing microcontrollers:
                        New sensor data is routed through the existing
                        Arduino_Thread or Teensy_Thread processes, using
                        the established serial communication protocols.
                        This is viable if the new sensor communicates via
                        USB serial (similar to existing accelerometer and
                        F/T sensors).

                      Option B — Add a new peripheral driver:
                        If the sensor uses a different protocol or requires
                        dedicated processing (e.g., a second GiGE camera
                        via a new GiGE_Thread, or a specialized USB device),
                        a new thread and software driver must be implemented
                        and integrated into the shared memory video buffer
                        architecture (Shared_Memory_Video_Buffers process).

                      The Tactile_Features_Calculator process may also need
                      to be updated if the new sensor produces raw signals
                      that require feature extraction (FFT, IIR filtering).

    Scope of change : Process-level change. The input schema of downstream
                      modules (Vision Classifier, Tactile Classifier) may
                      also need updating depending on what the new sensor
                      provides.

  Answer: No checkboxes selected
  ────────────────────────────────
  No characteristic triggered. The Grabber operates with its default sensor
  suite (GiGE Camera, ATI F/T Sensor, Teensy Accelerometer).

  Q4. Lighting conditions
------------------------------------------------------------------------

PURPOSE:
  Determines whether the physical environment provides adequate illumination
  for the vision system. The Grabber controls polarized LED lighting arrays
  via a Camera Light Controller.

TOOLTIP SHOWN TO USER:
  "Indicate if ambient lighting is sufficient for reliable vision processing,
   or if your application requires additional controlled lighting for
   consistent defect detection."

AVAILABLE ANSWERS:
  ┌────────────────────────────────┬──────────────────────────────────────────┐
  │ Option                         │ Meaning                                  │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ Sufficient lighting            │ Ambient environment provides adequate    │
  │                                │ illumination. No extra lighting hardware  │
  │                                │ needed.                                  │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ Need additional lighting       │ The environment requires supplemental    │
  │                                │ controlled lighting to ensure reliable   │
  │                                │ and consistent defect detection.         │
  └────────────────────────────────┴──────────────────────────────────────────┘

─────────────────────────────────────────────────────────────────
  CONSEQUENCES OF Q4
─────────────────────────────────────────────────────────────────

  Answer: "Sufficient lighting"
  ──────────────────────────────
  No characteristic triggered. Existing Camera Light Controller and
  Camera Exposure Time configuration manage normal operation.

  Answer: "Need additional lighting"
  ───────────────────────────────────

  [MODULE IMPACT] Grabber
    Characteristic  : "Addition of more lights for better illumination"
    Affects         : Process
    What changes    : Additional lighting can be added using the spare
                      channels available on the existing Camera Light
                      Controller microcontroller. The Camera Light Controller
                      manages polarized LED combines; extra LED units can
                      be connected to unused output channels without
                      requiring a new controller board. The control logic
                      within the Arduino_Thread process may need minor
                      updates to activate these additional channels.
    Scope of change : Hardware addition (LED units) + minor process-level
                      configuration update. No changes to Camera Exposure
                      Time topics or downstream vision pipelines required
                      beyond recalibrating exposure for the new lighting
                      conditions.

  Q5. Surface materials to work with
------------------------------------------------------------------------

PURPOSE:
  Identifies the materials of the objects to be inspected. Material
  properties directly affect classifier training requirements, profit
  calculations in scheduling, and localization strategy selection.

TOOLTIP SHOWN TO USER:
  "Select all material types you need to inspect. Different materials may
   require specialized detection methods and training data. Metal surfaces
   often have different reflective properties than wood or plastic."

AVAILABLE ANSWERS (checkboxes — multiple can be selected):
  ┌──────────────────────────────┬────────────────────────────────────────────┐
  │ Option                       │ Meaning                                    │
  ├──────────────────────────────┼────────────────────────────────────────────┤
  │ Metal (aluminum, steel)      │ Metallic surfaces with potentially high    │
  │                              │ reflectivity; may need polarized lighting. │
  ├──────────────────────────────┼────────────────────────────────────────────┤
  │ Wood                         │ Organic material with variable texture;    │
  │                              │ different defect signatures than metal.    │
  ├──────────────────────────────┼────────────────────────────────────────────┤
  │ Plastic                      │ Polymer surfaces; may have specific         │
  │                              │ optical properties (translucency, gloss).  │
  ├──────────────────────────────┼────────────────────────────────────────────┤
  │ Other materials              │ Non-standard materials (e.g., carbon fiber,│
  │                              │ composite, ceramic). Triggers follow-up.   │
  └──────────────────────────────┴────────────────────────────────────────────┘

CONDITIONAL FOLLOW-UP (shown when "Other materials" is checked):
  Sub-question : "Specify other material types:"
  Input type   : Free-text field
  Placeholder  : "e.g., carbon fiber, composite, ceramic..."
  Purpose      : Records the specific material for documentation and to
                 assist partners in collecting appropriate training data.

─────────────────────────────────────────────────────────────────
  CONSEQUENCES OF Q5
─────────────────────────────────────────────────────────────────

  Answer: Any material checkbox selected
  ────────────────────────────────────────

  [MODULE IMPACT 1] Orienteering Solver
    Characteristic  : "Material"
    Affects         : DefectProfitCalculator, Defect Information
    What changes    : The material type directly influences two internal
                      processes of the Orienteering Solver:

                      DefectProfitCalculator:
                        The function used to compute the profit of resolving
                        a defect must account for material-specific repair
                        economics. For example, a dent in steel may carry
                        different repair cost and value than a dent in plastic
                        or carbon fiber. The profit model must be calibrated
                        to the target material.

                      Defect Information (DefectInformation process):
                        The service time required to address a defect is
                        material-dependent. Harder materials may require
                        longer polishing or rework times. Softer materials
                        may deform under excessive force. The service time
                        lookup table or function must be updated for the
                        new material.

                      This may also interact with the Problem_description
                      process if material-specific time penalties or
                      constraints apply.

    Scope of change : Data/calibration-level change. Partners must provide
                      material-specific profit and service time specifications.

  [MODULE IMPACT 2] Localiser
    Characteristic  : "Material Y"
    Affects         : Process
    What changes    : The localization approach (the concrete implementation
                      of the Data_processing and Data_publication processes
                      within the Localiser module) must be selected based on
                      the material. The system supports multiple approaches:
                        - Approach 1: No mesh required (model-free)
                        - Approach 2: Uses material-specific geometric models
                        - Approach 3: More advanced model-based approach
                      When specific materials are specified, approaches 2 or 3
                      become applicable (or necessary). The Localiser's
                      common interface is designed to be material-agnostic
                      so that different implementations can be swapped.
    Scope of change : Process-level; the correct localization implementation
                      must be selected and configured for the target material.

  [MODULE IMPACT 3] Tactile Sensor
    Characteristic  : "Different materials, object sizes, dirt/dent types,
                       and time constraints"
    Affects         : Input
    What changes    : The Tactile Classifier System's machine learning model
                      (stored as a .joblib file, loaded by the Load_model
                      process) must be retrained on data collected from the
                      new material. The tactile signature (force patterns,
                      acceleration signatures, friction characteristics)
                      varies significantly between materials. The retraining
                      pipeline involves:
                        1. Pre_calculations: Collect and preprocess new
                           material-specific tactile data
                        2. Neural_network: Retrain the CNN-LSTM or LSTM-CNN
                           hybrid model on the new dataset
                        3. Ensemble: Optionally retrain ensemble models
                        4. Load_parameters: Update parameter.csv to match
                           new training configuration
                      The trained model then feeds back into the Prepare_data
                      and Make_predictions processes during runtime.
    Scope of change : Requires collection of new labeled training data for
                      the target material, followed by model retraining and
                      validation.

  [FLAG RAISED] Retraining Required
    Type    : Error-level data flag
    Message : "New material selected — vision and tactile classifiers must
               be retrained on data covering this material."
    Reason  : Both the Vision Classifier System (visual appearance changes
              per material) and the Tactile Classifier System (tactile
              signatures change per material) require new training data and
              model retraining for any new material not previously covered
              in the training dataset.

  Answer: No materials selected
  ──────────────────────────────
  No material-related characteristics are triggered. The system assumes it
  operates on previously characterized materials from existing training data.

─────────────────────────────────────────────────────────────────
  CONSEQUENCES OF Q6
─────────────────────────────────────────────────────────────────

  Any answer for object size (if at least one selection is made):

  [MODULE IMPACT] Tactile Sensor
    Characteristic  : "Different materials, object sizes, dirt/dent types,
                       and time constraints"
    Affects         : Input
    What changes    : Object size is one of the factors determining how
                      training data must be collected and how the tactile
                      model is trained. For large objects, the robot's
                      probe path and surface contact dynamics may differ

  Note: Object size does not currently trigger a specific characteristic for
  the Orienteering Solver, Grabber, or Localiser beyond what is captured by
  material and defect type answers. However, it contributes to the Tactile
  Sensor's broad "different use cases" characteristic trigger.

  Q7. 3D mesh availability
------------------------------------------------------------------------

PURPOSE:
  Determines whether a 3D mesh or CAD model of the object to be inspected
  is available. This is foundational for the Localiser module, which needs
  a mesh to perform model-based localization.

TOOLTIP SHOWN TO USER:
  "Indicate whether a 3D mesh or CAD model of the object is available. Mesh
   availability determines whether model-based or model-free localisation is
   used, and affects vision classifier configuration."

AVAILABLE ANSWERS:
  ┌────────────────────────────────┬──────────────────────────────────────────┐
  │ Option                         │ Meaning                                  │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ Available                      │ A 3D mesh (.off, .stl, .obj) or CAD      │
  │                                │ model of the object exists and is ready  │
  │                                │ for use.                                 │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ In preparation                 │ A mesh is being created or acquired but  │
  │                                │ is not yet ready. Triggers follow-up to  │
  │                                │ capture readiness status.                │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ Not available                  │ No mesh exists; model-free localisation  │
  │                                │ must be used, or scanning must be        │
  │                                │ initiated.                               │
  └────────────────────────────────┴──────────────────────────────────────────┘

CONDITIONAL FOLLOW-UP (shown when "In preparation" is selected):
  Sub-question : "Current mesh status:"
  Input type   : Dropdown selector
  Options      :
    - CAD model exists   (mesh can be derived from existing CAD)
    - Needs 3D scanning  (physical object must be scanned)
    - Unknown            (status not yet determined)
  Purpose      : Provides actionable detail on what steps remain before
                 the mesh is available for use.

─────────────────────────────────────────────────────────────────
  CONSEQUENCES OF Q7
─────────────────────────────────────────────────────────────────

  Answer: "Available"
  ────────────────────

  [MODULE IMPACT] Localiser
    Characteristic  : "Material Y"
    Affects         : Process
    What changes    : With a 3D mesh available, the Localiser can use approach
                      2 or 3 (model-based localization). The Data_processing
                      process can use the mesh file (.off, .stl, or .obj) to
                      compute accurate TF2 transforms between the robot and
                      the object. The Data_publication process can also
                      publish the ROS2 robot_description based on the mesh.
                      Model-based localization typically achieves higher
                      accuracy and repeatability compared to model-free
                      approaches.
    Scope of change : Process-level selection; mesh file must be provided as
                      an input parameter to the Localiser.

  Answer: "In preparation"
  ─────────────────────────

  [MODULE IMPACT] Localiser
    Characteristic  : "Material Y"
    Affects         : Process
    What changes    : The localization module configuration is considered
                      provisional. The final selection of approach 2 or 3
                      (vs. approach 1 / model-free) must be deferred until
                      the mesh is finalized. A placeholder configuration
                      should be used during development, with a mandatory
                      revisit once the mesh is ready.
    Scope of change : Process-level provisional configuration.

  [FLAG RAISED] 3D Mesh In Preparation
    Type    : Warning-level assumption validity flag
    Message : "Localisation module configuration is provisional until the
               mesh is available. Revisit this assessment when ready."
    Reason  : The localization approach cannot be finalized without the
              mesh. Any configuration decisions made in this state carry
              the risk of requiring revision.

  Answer: "Not available"
  ─────────────────────────

  [MODULE IMPACT] Localiser
    Characteristic  : "Material Y"
    Affects         : Process
    What changes    : Without a 3D mesh, only model-free localization
                      (approach 1) is available. The Data_processing process
                      must be configured for sensor-only entity tracking
                      without geometric priors. This is typically less
                      accurate and less robust than model-based approaches.
                      Steps to obtain a mesh (3D scanning or CAD retrieval)
                      should be initiated as a priority.
    Scope of change : Process-level; critical prerequisite for higher-quality
                      localization.

  [FLAG RAISED] 3D Mesh Missing — Critical
    Type    : Error-level data quality flag
    Message : "Localisation approach cannot be finalised without a mesh.
               Initiate 3D scanning or CAD retrieval before proceeding."
    Reason  : The absence of a mesh severely limits localization options.
              Partners must treat mesh acquisition as a blocking prerequisite
              for model-based localization deployment.

  6. SECTION D — DEFECT DETECTION
================================================================================

------------------------------------------------------------------------
  Q8. Types of defects to detect
------------------------------------------------------------------------

PURPOSE:
  Identifies the categories of surface defects the system must detect and
  address. Different defect types require different detection modalities
  (visual vs. tactile), affect how the Orienteering Solver calculates profit
  and service times, and may require specific training data.

------------------------------------------------------------------------
  Q9. Time constraints
------------------------------------------------------------------------

PURPOSE:
  Determines whether the robot's inspection/rework task is subject to a
  hard time limit. Time constraints fundamentally change the mathematical
  formulation of the scheduling problem solved by the Orienteering Solver.

TOOLTIP SHOWN TO USER:
  "Indicate if your inspection task has time limits. Tight deadlines affect
   motion planning strategies and may require prioritizing certain areas.
   Specify the maximum time allowed for completing the inspection."

AVAILABLE ANSWERS:
  ┌────────────────────────────────┬──────────────────────────────────────────┐
  │ Option                         │ Meaning                                  │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ No time constraints            │ The task can be completed without a      │
  │                                │ hard time budget. All defects can be     │
  │                                │ visited.                                 │
  ├────────────────────────────────┼──────────────────────────────────────────┤
  │ Tight deadlines/timeframe      │ The task must be completed within a      │
  │ required                       │ finite time budget (e.g., production     │
  │                                │ cycle time). Triggers time specification │
  │                                │ sub-question.                            │
  └────────────────────────────────┴──────────────────────────────────────────┘

CONDITIONAL FOLLOW-UP (shown when "Tight deadlines/timeframe required"):
  Sub-question : "Specify time constraint:"
  Input type   : Numeric value + unit selector
                 (Unit options: Seconds / Minutes [default] / Hours)
                 Default value: 2 minutes
  Purpose      : Captures the hard time limit to be passed to the
                 Orienteering Solver's /configuration_module/max_time
                 and /configuration_module/max_compute_time parameters.

─────────────────────────────────────────────────────────────────
  CONSEQUENCES OF Q9
─────────────────────────────────────────────────────────────────

  Answer: "No time constraints"
  ──────────────────────────────

  [MODULE IMPACT 1] Orienteering Solver
    Characteristic  : "No time constraint"
    Affects         : Problem Description
    What changes    : When there is no time budget, the Orienteering Problem
                      formulation is no longer appropriate (the OP implicitly
                      assumes not all nodes can be visited within the budget).
                      Instead, the Problem_description process reformulates
                      the task as the Travelling Salesman Problem (TSP), where
                      all defects must be visited in the optimal sequence to
                      minimize total travel time. The Algorithm process must
                      be reconfigured to use a TSP solver instead of an OP
                      solver. The time_restriction input can be ignored.
    Scope of change : Problem formulation change; the Algorithm and
                      Hyperparameters processes must be updated accordingly.

  [MODULE IMPACT 2] Localiser
    Characteristic  : "No time constraint"
    Affects         : Process
    What changes    : The Localiser's Data_processing pipeline can omit any
                      time-constrained processing shortcuts. Without a time
                      budget, the localization algorithm can run more
                      exhaustive search or refinement cycles, potentially
                      improving localization accuracy at the cost of
                      additional computation time.
    Scope of change : Process-level configuration; the time deadline check
                      within the Localiser can be removed or relaxed.

  Answer: "Tight deadlines/timeframe required"
  ─────────────────────────────────────────────

  [MODULE IMPACT] Orienteering Solver
    Characteristic  : "Addition of defects have to happen in a certain
                       timeframe"
    Affects         : Problem Description
    What changes    : The problem formulation changes from the standard
                      Orienteering Problem to the Orienteering Problem with
                      Time Windows (OPTW). In OPTW, certain defects must be
                      addressed within specific time intervals (time windows)
                      in addition to the overall time budget constraint.
                      The Problem_description process must encode these time
                      windows. The Algorithm and Hyperparameters processes
                      must be updated to use an algorithm capable of handling
                      time window constraints (not all OP solvers support
                      this).
                      The time specification entered by the user (value +
                      unit) flows into the /configuration_module/max_time
                      topic, which is consumed by the OP solver at runtime.
    Scope of change : Problem formulation change and algorithm selection
                      update. Also affects the max_compute_time configuration
                      to ensure the solver has enough compute budget to
                      handle the more complex OPTW formulation.

  CONSEQUENCES OF Q10

  Answer: "Standard profit calculation"

  /get_profit service implementation are used as-is.

  Answer: "Custom profit/priority criteria"
  ──────────────────────────────────────────

  [MODULE IMPACT] Orienteering Solver
    Characteristic  : "Profit definition changes"
    Affects         : Problem Description, DefectProfitCalculator
    What changes    : Two components are affected:

                      Problem Description (Problem_description process):
                        A custom profit definition may change the OP variant.
                        If profits vary continuously with service time (not
                        just a fixed value per defect), the problem becomes
                        the Orienteering Problem with Variable Profits (OPVP).
                        The Problem_description process must encode the new
                        profit semantics, and the Algorithm and Hyperparameters
                        must be updated for the chosen OP variant.

                      DefectProfitCalculator:
                        The internal placeholder function used to calculate
                        defect profit changes entirely. The default
                        implementation (based on car body rework economics)
                        must be replaced or extended with a new implementation
                        that reflects the custom profit criteria. This is a
                        code/logic modification, not just a parameter change.
                        The /get_profit service interface remains the same
                        but its internal logic changes.

    Scope of change : Both a problem formulation change and a code-level
                      modification to the profit calculation logic. Partners
                      must supply the new profit function specification.

  [FLAG RAISED] Human Validation Required: Custom Profit Function
    Type    : Human oversight flag
    Message : "Custom profit criteria cannot be verified automatically.
               A domain expert must sign off before deployment."
    Reason  : A custom profit function involves domain knowledge and
              business logic that cannot be validated by the COT system.
              The system flags this for mandatory expert review to prevent
              incorrect prioritization in production.

  Icon      : 🔗

  Action    : Do not attempt to implement all changes simultaneously. Use a

              before integrating. Conduct cross-module integration tests
